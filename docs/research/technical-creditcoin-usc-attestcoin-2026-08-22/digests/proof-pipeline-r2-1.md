# Digest: proof-pipeline (round 2)

**Summary:** Round 1's central missing artifact was found: the Solidity verification surface lives in gluwa/USC-Builder-Examples, not in custom-contracts-bridging or the docs precompile list. The 0x0FD2 precompile is `INativeQueryVerifier` with a single method `verifyAndEmit(uint64 chainKey, uint64 height, bytes encodedTransaction, MerkleProof, ContinuityProof) returns (bool)` — it attests a transaction blob you supply rather than returning a decoded receipt; decoding happens in your own contract via EvmV1Decoder.sol. That decoder exposes far more than round 1 could confirm: receipt-level `receiptStatus`, `receiptGasUsed` (uint64), `receiptLogs[]` with `address_`/`topics`/`data`, and `receiptLogsBloom`; and transaction-level `from`, `to`, `value`, `nonce`, `gasLimit`, `data` — so transaction sender IS available, not merely event-level from, though it is decoded pre-extracted from the payload with no on-chain ecrecover. The deployed prover question resolves by triangulation: `hasPrecompile()` hardcodes chain IDs 102030/102031/102033, and docs.creditcoin.org/environments/testnet gives Creditcoin testnet EVM ChainId 102031 — so testnet runs the native query verifier (the fast branch), and neither shipped interface mentions STARKs at all. MAX_BATCH_SIZE/MAX_BATCH_RANGE appear nowhere in the precompile interface or the Solidity verification library, and the precompile takes exactly one transaction per call, so batching is SDK-side query convenience and a contract may verify N source transactions in one Creditcoin transaction bounded only by gas. Non-inclusion is now negative evidence rather than absent evidence: both verifier interfaces were read in full and contain no absence primitive, and `ProofKind` has a single variant `BinaryMerkle`. Block time remains undocumented after two rounds.

## Contradictions
- Round 1 framed the prover choice as 'native query verifier vs legacy STARK'. Neither shipped Solidity interface references STARKs at all — the actual runtime fork in the code is 'precompile present vs not present' (hasPrecompile() chain-ID check with a code-existence fallback), routing to INativeQueryVerifier or IUSCProofVerifier respectively. The STARK framing may be stale, may describe a node-internal detail invisible at the interface layer, or may describe a superseded architecture.
- Round 1 recorded that docs.creditcoin.org/wallets/advanced/precompiled-smart-contracts.md lists 13 precompiles with none at 0x0FD2, while INativeQueryVerifier.sol hardcodes 0x0000000000000000000000000000000000000FD2 and gates on Creditcoin chain IDs. The docs precompile list is incomplete relative to the shipped code — treat the Solidity source as authoritative over that docs page.
- Round 1 treated transaction-level `from` as possibly unrecoverable (only event-level from available). EvmV1Decoder decodes `from` as a first-class CommonTxFields address. The nuance that reconciles the concern: it is pre-extracted from the payload rather than ecrecover-derived on-chain, so it is available but attestation-trusted.
